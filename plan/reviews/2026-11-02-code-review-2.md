## Clean (checked and correct)

- **IMAP command construction:** arguments pass through `quote()` (rejects CR, LF, NUL, escapes `"` and `\`), UID sets are numeric, flags are whitelisted, `X-GM-RAW` queries are quoted, so no command injection; fetches use `BODY.PEEK[]` (nothing is marked read); `ImapConfig` redacts the password in `Debug`; plain IMAP needs `FA_ALLOW_PLAIN_IMAP`, otherwise port 993 is implicit TLS and every other port is `STARTTLS` with no fallback to plain.
- **Ingestion idempotency:** `message` inserts use `ON CONFLICT (source_id, remote_id) DO NOTHING`, listings are filtered through `existing_remote_ids`, `mail.process` and `mail.sync` carry idempotency keys, a UIDVALIDITY change is detected in `scan`, `fetch_many` and `locate` (with an RFC 822 id check for re-fetched messages), the per-run cap of 2000 resumes through a continuation job, and a partial run never advances the cursor past what was handled (`state(processed)`).
- **Secrets and logs:** the IMAP password is stored through `SecretRepo` (envelope encryption), `sync.rs` logs ids, counts and timings only, `Http::send` logs only the host and strips the URL from errors, calendar errors are passed through `scrub` (URLs and credentials replaced) before they are stored, the ntfy token header is marked sensitive, and neither the topic nor the token appears in logs or errors.
- **Untrusted mail parsing:** `fa-rules/src/parse.rs` has a no-panic test over malformed and deeply nested input; scripts, frames and plugins are stripped from stored HTML (and the web app never renders it: no `v-html` in `apps/web/src`); PDFs over 5 MB are not decoded; ICS parts in mail are read by `fa-rules` without recurrence expansion, so a hostile mail cannot reach `expand`.
- **ICS, CalDAV and recurrence:** feed bodies are capped at 10 MB after gzip (the decoded size is what is counted), redirects re-run the scheme and private-address check, `webcal://` becomes https, hostile `FREQ=SECONDLY` rules are bounded (65 535 generated, 5000 kept per component), `UNTIL` before `DTSTART` and unknown time zones are handled with a warning, DST is applied on the wall clock; the multistatus parser (`quick_xml`) resolves only the five predefined entities, so there is no entity expansion.
- **Outbound clients:** every HTTP client is built in `fa-connectors/src/http.rs`; production wiring uses `Http::with_policy(allow_http, allow_private_hosts)` for mail, calendar, OAuth and weather; the custom resolver filters at connect time (no DNS rebinding window) and the redirect policy re-checks each hop. The only deliberate exception is ntfy (LAN, `Http::new(true)`).
- **Task authorisation:** every route in `tasks.rs` runs an `authz` check before the service; `skip`, `accept` and all definition, routine, list and absence routes need `ManageTasks` (adult user, never a device, elevated or not); `complete`, `reopen` and `tick` use `CompleteTask` with the list's completion policy and the dashboard override; children cannot see tasks assigned to others and `routines/today` forces the child's own id; `PATCH` routes require `If-Match` (428 without) and the store updates `WHERE version = $n`; `tick_step` checks that the step belongs to the task; plain devices naming a `member` is by design (D-064 dashboard completion) and the audit row records the device.
- **Notify authorisation and content:** `ManageNotifyPrefs` is self, or an adult for a child, never a device; the topic is hidden from other children; `copy_to_member` must be another active adult and copy rows are not re-copied (`copy:` dedupe key); quiet hours defer instead of dropping; header values have CR/LF removed.

**Questions for the user.**

1. **Email-origin tasks (C2-21).** Once a task made from a private mailbox's mail is accepted, should it be an ordinary household task that every adult (and the dashboard) sees, or should it keep following the mailbox's visibility (owners only) until completed? Suggested default: follow the mailbox while `suggested`, household once accepted; configurable per mail source.
2. **CalDAV on other hosts (C2-15).** May a CalDAV server send us to a different host (iCloud does)? Suggested default: same registrable domain only, with a "trust other hosts" toggle per source, off.
3. **Self-hosted mail on the LAN (from the Clean notes on IMAP).** `FA_ALLOW_PLAIN_IMAP` and `FA_IMAP_TLS_INSECURE` are process-wide, tests-only switches, so a Dovecot with a private CA cannot be used safely. Should a source be able to pin a certificate or CA (suggested: yes, optional PEM per source) and allow plain IMAP only to private hosts (suggested: off)?
4. **Maximum message size (C2-01, C2-05).** What should happen to a message over the limit? Suggested: configurable limit (default 40 MB), message stored as headers only with a "too large" marker so it can still be categorised, shown in Settings.
5. **What ntfy sees (C2-30).** Notification titles can contain mail subjects and bill payees. Should there be a "generic text only" mode (default on when `ntfy_url` is not on the LAN or tailnet, off otherwise)?
