# M0 Skeleton: Implementation Plan

## Goal
Deliver the platform described in `arch/Platform.md` so that every later milestone can add features without reworking the foundations. **Done** means meeting Platform.md §11:
1. The workspace builds, and GitHub Actions `ci.yml` is green.
2. Migrations exist for Identity, Audit, Secret, job, and schedule, with RLS on.
3. `config import` of the example household works, and `config export` round-trips it.
4. Login, logout, and sessions work. The RBAC policy has tests. Device pairing and PIN elevation work.
5. The Vue shell has login, a member list, and a `/dashboard` placeholder with a device token, an SSE heartbeat, and the keep-alive measures.
6. The compose example comes up, is reachable over tailscale from a phone, a backup lands on the NAS, and a restore rehearsal passes.

## Contracts fixed up front (so tasks can run in parallel)
**Crates:** `fa-domain`, `fa-store`, `fa-config`, `fa-auth`, `fa-jobs`, `fa-api`, and the bins `fa-server` and `fa-gpu-agent` (the latter a stub only).

**Dependency rule:** `domain` ← `store` ← {`config`, `auth`, `jobs`} ← `api` ← `fa-server`.

**Migrations** are owned by `fa-store` only (`crates/fa-store/migrations/`). The tables are `household`, `member`, `user_account`, `session`, `device`, `device_elevation`, `notify_pref`, `audit_entry`, `secret`, `job`, and `schedule`.

**HTTP API v1 (M0)** (JSON; errors use `application/problem+json`; mutating requests need the `X-FA-Request: 1` header):
| Method & path | Actor | Purpose |
|---|---|---|
| `GET /healthz`, `GET /readyz` | none | liveness, and DB plus migrations ready |
| `POST /api/v1/auth/login` `{username, password}` | none | sets the session cookie |
| `POST /api/v1/auth/logout` | user | |
| `GET /api/v1/me` | user, device | `{actor: {kind: user\|device\|elevated_device, member?, device?}, household}` |
| `GET /api/v1/members` | user, device | adults get every field. Children and devices get the public fields (display_name, role, avatar, color) |
| `POST /api/v1/members`, `PATCH /api/v1/members/{id}` | adult | create or update a member (child settings included, other adults excluded) |
| `POST /api/v1/members/{id}/account` `{username, password}` | adult | create the account (child password ≥4, adult ≥12), D-031 |
| `POST /api/v1/members/{id}/account/password` | adult (child target) or self | reset the password |
| `PUT /api/v1/members/{id}/pin` `{pin}` | the adult themself | set the PIN (4 to 6 digits) |
| `GET /api/v1/devices`, `POST /api/v1/devices` `{name}` → `{id, token, pair_url}`, `DELETE /api/v1/devices/{id}` | adult | dashboard device pairing and revocation |
| `POST /api/v1/device/elevate` `{member_id, pin}` → `{expires_at}` | device | PIN step-up for 5 minutes. 5 failures lock it for 15 minutes |
| `GET /api/v1/sessions?member=…`, `DELETE /api/v1/sessions/{id}` | adult | revoke child sessions |
| `GET /api/v1/stream` | user, device | SSE: `heartbeat` every 15 s, `member.updated`, with `Last-Event-ID` support |
| `GET /api/v1/openapi.json` | none (dev) | utoipa |

**Auth transport:**
- Users get the `fa_session` cookie (HttpOnly, Secure (off in dev over http), SameSite=Lax). It rolls for 30 days for adults and 180 days for children.
- Devices send `Authorization: Bearer <token>`.

**Household TOML** (`config/examples/household.example.toml`) holds a fictional family with `example.com` addresses only. It has `[household]` (name, tz, location) and `[[members]]` (key, display_name, role, birthdate?, grade?, interests, hobbies, responsibilities). It contains no secrets or passwords: accounts are created with the `fa-server user add` command.

## Orchestration rules (main session)
- Run each wave's tasks as **parallel sub-agents: Sonnet 5.5, medium effort**, each with its brief as the prompt.
- **Ownership:** each brief lists the paths it *owns*. An agent must not edit paths it doesn't own. If it needs a change elsewhere, it reports it, and the main session applies it or routes it to the owner. The root `Cargo.toml` (workspace) belongs to T-01. Later tasks may only add dependencies to their own crate's `Cargo.toml`, using `workspace = true` entries that T-01 pre-declares.
- **Between waves**, the main session:
  1. reviews each report;
  2. runs `cargo build --workspace && cargo test --workspace` (and the web checks);
  3. fixes small integration issues itself;
  4. updates the task's front-matter status;
  5. logs the outcome.
- **Done for a task** means its acceptance commands pass and its report lists any deviations from the arch docs. A deviation needs either an arch doc update or a question.
- **Public repo (D-035):** no real names, addresses, or emails anywhere. Fixtures use `example.com`.
- Agents don't commit. The user commits.

## Risks
| Risk | Mitigation |
|---|---|
| sqlx compile-time macros need a live DB or `.sqlx` data | T-01 provides dev Postgres. T-04 commits the `.sqlx` data (`cargo sqlx prepare`), and CI uses `SQLX_OFFLINE=true` |
| RLS combined with connection pooling | Use `SET LOCAL app.household_id` inside each transaction (fa-store `with_household(tx)`). T-04 tests it |
| Parallel agents sharing one `target/` | Cargo's lock serialises builds. That costs time but is safe |
| API contract drift between T-08 and T-09 | The contract table above is the source of truth. T-09 generates its client from T-08's `openapi.json` |
