# M3 Ingest: Implementation Plan

## Goal
Email ingest through the Gmail API or IMAP, the rules-only decision pipeline, deterministic classification and extraction, orgs/contacts/enrollments, bills, event proposals with calendar writes on approval, the approval inbox, email tasks, Gmail/IMAP actions with undo, and the labelling view, as designed in `arch/Ingest.md` (v1), `arch/Domain.md` (v5) and `arch/Frontend.md` (v3). **Done** means:
1. `scripts/ci-local.sh` (fresh Postgres, `SQLX_OFFLINE=true`) is green.
2. Both providers sync: Gmail API (wiremock tests: first sync, history incremental, 404 fallback, label changes, `invalid_grant`) and IMAP (tests and e2e against a real `greenmail/standalone:2.1.8` container: first sync, incremental by UIDNEXT, UIDVALIDITY reset, plain-IMAP refused unless `FA_ALLOW_PLAIN_IMAP`).
3. `mail.process` runs every email decision point through the 'Rules only' pipeline, records `decision` rows, links members (grade, class, name/alias, tags, gender terms), and extracts events (ICS, schema.org, date phrases), bills (templates, generic, PDF), tasks (action phrases, contact questions) and contact suggestions.
4. **Every extracted event becomes a proposal** (D-057); approving writes it to Google (`events.insert`) or CalDAV (`PUT`); dedupe stops duplicates; cancellations withdraw proposals or propose deletion.
5. The inbox lists events, bills, tasks and contacts; approve/reject works from the app and an elevated dashboard; expiry per D-061; `approval_needed` and `mail_time_sensitive` notifications reach ntfy (batched, immediate, digest-only and off modes).
6. Bills: a pay task on the adult pool; completing it marks the bill paid, reopening reopens it (D-059).
7. Auto actions per category (labels by default) on writable sources, all undoable for 30 days (D-058).
8. Labelling view: four decision points, balanced queue, eval-sample toggle and progress (D-062).
9. Visibility: owners or household per source; children never list messages (D-063). The RBAC tests cover every new action.
10. `config export` → `import` round-trips the new sections (secrets excluded).
11. The README is updated and its steps verified. `scripts/e2e.sh` passes, run by the main session.

## Environment notes
As in M2 (`plan/M2.md`): pnpm is `corepack pnpm@9`; `just` and `psql` are not installed; the dev DB is `postgres://fa:fa@127.0.0.1:55432/fa` and **holds the user's real household data: never read its rows (schema only)**. `.cargo/config.toml` sets `SQLX_OFFLINE=true`; set `SQLX_OFFLINE=false` explicitly only for `cargo sqlx prepare`. Tests use `#[sqlx::test]` or throwaway containers. Disk is tight (about 16 GB free on 2026-10-25): agents build with `CARGO_INCREMENTAL=0` and check `df -h /` first. IMAP tests use `greenmail/standalone:2.1.8` (verified by `docker pull` on 2026-10-25): plain IMAP on 3143, IMAPS on 3993 (self-signed), SMTP on 3025; users are auto-created on first login (`-Dgreenmail.auth.disabled` is **not** used; tests send mail by SMTP or IMAP `APPEND`).

### Pipeline engine (T-05, `fa-pipeline`)
```rust
pub trait Evaluator: Send + Sync { fn candidates(&self, dp: DecisionPointKey) -> Vec<Candidate>; }
pub struct Outcome { pub values: Vec<Candidate>, pub stage: StageKind, pub is_final: bool, pub version: PipelineVersionId }
impl Pipeline {
  pub fn new() -> Self;
  pub async fn ensure_defaults(conn, household) -> Result<()>;                   // delegates to mail_defaults::ensure
  pub async fn run(conn, household, dp, subject: Subject, eval: &dyn Evaluator) -> Result<Outcome>;
  pub async fn record_human(conn, household, dp, subject, value: Value, member: Option<MemberId>) -> Result<DecisionId>;
  pub async fn current(conn, dp, subject) -> Result<Option<Decision>>;          // latest final, else latest
  pub async fn all_current(conn, subject) -> Result<Vec<Decision>>;
}
```
`run`: load the active version; for each enabled stage in `ord`: `rules` → `eval.candidates(dp)`; multi-valued `email.member_link` keeps **every** candidate ≥ threshold (one per member), others keep the single best (ties: first). Accepted → insert `decision` rows (`is_final = true`, `stage_kind = rules`, `source` = candidate source) and return. `knn`/`system_one`/`llm` are unavailable in M3 → `on_unavailable`: `skip` continues, `wait`/`queue` behave as `skip` and log once. `human` (last) → insert the default value as `is_final = false`, `stage_kind = human`, `source = "default"` and return. A version whose last enabled stage is not `rules`/`human` is rejected by `validate_version` (no API in M3, but unit-tested).

### fa-calendar additions (T-11)
- Job `calendar.route{event}`: (1) **dedupe** via `EventRepo::dedupe_candidates(conn, start ± 1 day)` (same `dedupe_key`, or `title_similarity ≥ 0.85` and start within ±60 min / same date for all-day, or same `remote_uid`): a match inserts `event_message(existing, message)` and deletes the extracted row; (2) **cancellations** (`cancelled = true` on the extracted row): a matching proposed event → `expired`; a matching event we wrote (`origin = extracted, status = written`) → `pending_cancel = true` (proposal) or, with `events_auto_write` on, enqueue `calendar.delete{event}`; others → ignore; the cancellation row is deleted; (3) **route** through `fa_pipeline::Pipeline::run(event.calendar_route)` with an evaluator: org `default_calendar_id` 0.95, the single `is_default_target` calendar among the linked members' calendars 0.9, the household default target 0.7 (only calendars on `writable` sources); (4) **gate**: `events_auto_write && confidence ≥ extract_threshold && route ≥ route_threshold` → `approved` + `calendar.write{event}`; else `proposed` + `approval_needed` outbox rows to every adult (key `approval:event:{event}:{member}`).
- `CalendarService::approve_event(household, event, EventApproval, by: Option<MemberId>)` (records a `human` decision for the route; `approved`; job `calendar.write{event}`), `reject_event` (`rejected`, human decision), `approve_cancel` / `reject_cancel` for `pending_cancel`, `proposals(household) -> Vec<EventProposalView>`.
- Job `calendar.write{event}`: Google `events.insert` (store the returned `iCalUID` as `remote_uid` and the event id in `source_ref.external_url`'s htmlLink) or CalDAV `PUT {calendar}/{uid}.ics` with our UID `fa-<event id>@family-assistant`; success → `written`, `calendar_id` = target; failure → `write_error`, stays `approved` (retry by the job policy; the inbox shows the error). Job `calendar.delete{event}` similarly. The next sync must **not** duplicate or clobber written rows (T-03 makes `upsert_synced` skip rows with `origin = extracted`, and `delete_unseen_in_window` already only deletes `synced`).
- Google writes need `https://www.googleapis.com/auth/calendar.events`; a missing scope → `write_error = "reconnect with calendar write access"`.

## Risks
| Risk | Mitigation |
|---|---|
| Gmail OAuth can't be exercised in CI | wiremock for every Gmail call; real IMAP (greenmail) for the end-to-end path; the provider trait keeps everything after sync shared |
| Date-phrase false positives | Confidence ≤ 0.7, and in M3 every event is a proposal anyway (D-057) |
| Untrusted mail content (HTML, PDFs, regexes) | `html2text`/`scraper` only (no script execution), PDF size cap + timeout in `spawn_blocking`, regex size limits, content never logged |
| Duplicate events across sources and re-syncs | `dedupe_key`, similarity, ICS UID, `event_message` provenance, `upsert_synced` skipping extracted rows |
| Disk pressure from new deps (pdf-extract, scraper, async-imap) | `CARGO_INCREMENTAL=0`, cleaning between waves, `cargo clean` if `target/debug/deps` passes 15 GB |
