# M1 Dashboard core: Implementation Plan

## Goal
Members, weather (with rules), calendar read (Google, CalDAV, ICS), and the real dashboard, as designed in `arch/Feeds.md` and `arch/Frontend.md`. **Done** means:
1. `scripts/ci-local.sh` (fresh Postgres, `SQLX_OFFLINE=true`) and GitHub `ci.yml` are green.
2. Calendar sync works for all three kinds:
   - **ICS:** fixture feed.
   - **CalDAV:** against a real Radicale container in e2e.
   - **Google:** wiremock tests, plus live in H-06.

   Tests cover recurrence expansion with EXDATE and RECURRENCE-ID overrides, all-day events, DST, Google incremental sync (including the `410` full resync), and `needs_reauth`.
3. The API applies the visibility rules (D-036) for child users and dashboard devices, with tests.
4. Weather works end to end: fetch (Open-Meteo stub in tests), snapshots, the DSL parser and evaluator, default rules turning into advisories (with dedupe), and retention.
5. The dashboard works:
   - per-device layout from Settings → Devices;
   - the clock, weather, advisories, agenda, week, and members panels;
   - live updates from the **worker running as a separate process** reach it through the ChangeBus;
   - the offline snapshot shows while the server is unreachable.
6. The app shell has Today, Calendar, member avatars, and Settings (household, calendars, weather, devices, status).
7. `config export` → `import` round-trips the new sections, with secrets excluded and sources coming back as `needs_reauth`.
8. The README is updated and its steps verified by running them. The demo runs on real hardware (H-07).

## Contracts fixed up front
### Crates
- **New:** `fa-connectors` (leaf: no `fa-*` dependencies), `fa-calendar`, and `fa-weather`.
- **Extended:** `fa-domain`, `fa-store`, `fa-auth`, `fa-config`, `fa-api`, and `fa-server`.

**Dependency rule:** `fa-connectors` is standalone. `fa-calendar` and `fa-weather` depend on {`fa-domain`, `fa-store`, `fa-jobs`, `fa-connectors`}. `fa-auth` adds `fa-connectors` (for the Google token exchange). `fa-config` doesn't depend on any feature crate: `fa-server config import` validates weather-rule DSL through `fa-weather` before writing. `fa-api` and `fa-server` wire everything together.

**Process config injection:** feature crates never read `fa-config`. `fa-server` passes settings (Open-Meteo URL, Google client, public URL, `allow_http_feeds`) into their constructors as plain structs that each crate defines.

**W0 (main session, before Wave 1):**
1. Add the three new crates as empty lib crates to the workspace.
2. Pre-declare these workspace dependencies: `reqwest 0.13` (default-features off; `rustls`, `json`, `gzip`), `oauth2 5`, `icalendar 0.17`, `rrule 0.14`, `quick-xml 0.42` (`serialize`), `wiremock 0.6`, `url 2`, `bytes`, `sha2`.
3. Check the exact feature names with `cargo add --dry-run`.

The root `Cargo.toml` stays main-session owned.

### Domain types (T-01, in `fa-domain`)
- **IDs:** `OAuthAccountId`, `CalendarSourceId`, `CalendarId`, `EventId`, `WeatherRuleId`, and `AdvisoryId`.
- **Enums:** `Units`, `SourceKind`, `SourceState`, `Visibility {Full, Busy}`, `EventOrigin`, `EventStatus`, `RuleAction`, `Severity`, `RuleStatus`, and `SuggestedBy`.
- **Pure function:** `fa_domain::calendar::view(event_meta, calendar_meta, viewer, household_flags) -> Visibility`. This implements Feeds.md §3.5 and is used by both fa-calendar and fa-api.
- **Trait:** `fa_domain::AccessTokenProvider` (`#[async_trait] fn access_token(&self, household, OAuthAccountId) -> Result<String, TokenError{NeedsReauth, Other(String)}>`). fa-auth's `OAuthService` implements it, and fa-calendar consumes it, so neither depends on the other.
- **Policy:** new actions `ManageCalendarSource` (resource `Source{owner: Option<MemberId>}`, D-006 rules), `ReadCalendar`, `ManageWeatherRules`, `DismissAdvisory` (any user or device), and `ManageDeviceSettings` (adult). The exhaustive policy tests are extended to cover them.
- **DTOs:** every request and response DTO in the table below derives `serde` and `utoipa::ToSchema`. M0 DTOs gain `ToSchema` too, and `MemberView` becomes an untagged union of `MemberPublic` and `MemberFull`. Both gain `avatar_url: Option<String>` (`/api/v1/members/{id}/avatar?v=<sha256 prefix>`, or null without an avatar).
- **`DashboardSettings.members`** serialises as the string `"all"` or a JSON array of member IDs (a serde untagged enum).

### HTTP API v1 additions (M1)
The M0 conventions still apply: problem+json, `X-FA-Request`, If-Match, and 409/428.

| Method & path | Actor | DTOs and notes |
|---|---|---|
| `GET /api/v1/household` | user, device | `HouseholdView{name, tz, location?, units, calendar_past_days, calendar_future_days, weather_retention_days, private_events_as_busy, google_oauth_enabled, version}`. `google_oauth_enabled` is read-only (true when `FA_GOOGLE_CLIENT_ID`/`_SECRET` are set) |
| `PATCH /api/v1/household` | adult | `HouseholdPatch`. Publishes `household.updated` |
| `PUT /api/v1/members/{id}/avatar` (raw body, `Content-Type` image/png, jpeg, or webp, ≤ 512 KB) · `DELETE` | adult (self or a child) | 413 if too large, 415 for other types. Publishes `member.updated` |
| `GET /api/v1/members/{id}/avatar` | user, device | `ETag` (sha256), `Cache-Control: private, max-age=86400` |
| `GET /api/v1/oauth/google/start?return_to=` | adult | 302 to Google (PKCE S256, `access_type=offline`, `prompt=consent`, scope `calendar.readonly` + `openid email`) |
| `GET /api/v1/oauth/google/callback?code&state` | adult (same session) | creates or updates the `oauth_account`, then 302 to `/oauth/done?account=<id>&return_to=…` (or `?error=…`) |
| `GET /api/v1/oauth/accounts` | adult | `OAuthAccountView[]` (own accounts and children's; never secrets) |
| `GET /api/v1/calendar-sources` | adult | `SourceView{id, kind, name, owner?, masked_url?, username?, state, last_synced_at?, last_error?, poll_minutes, version}` |
| `POST /api/v1/calendar-sources` | adult | `NewSource = Google{oauth_account, name} \| CalDav{name, url, username, password} \| Ics{name, url}` (+ owner?). Discovers synchronously (20 s timeout) and returns `SourceView` plus `CalendarView[]` (new calendars disabled) |
| `POST /api/v1/calendar-sources/test` | adult | the same body without saving → `{ok, calendars[], sample_events[≤3], error?}` |
| `PATCH /api/v1/calendar-sources/{id}` · `DELETE` (archive) | adult (owner rules) | `SourcePatch{name?, poll_minutes?, credentials?}`. A credential change resets the state to `ok` and enqueues a sync |
| `POST /api/v1/calendar-sources/{id}/sync` | adult | enqueues `calendar.sync`, returns 202 |
| `GET /api/v1/calendars` | adult | `CalendarView{id, source, name, color, enabled, members[], version}` |
| `PATCH /api/v1/calendars/{id}` | adult | `CalendarPatch`. Publishes `calendar.updated` (full window) |
| `GET /api/v1/events?from&to&member?` | user, device | `EventView{id, calendar, title, location?, description?, start_at, end_at, all_day, start_date?, end_date?, members[], color, visibility, external_url?}`. Scoped per viewer and masked per `view()` (D-036). The range is capped at 400 days |
| `GET /api/v1/weather` | user, device | `WeatherView{fetched_at, current, hourly[48], daily[7], sunrise_today?, sunset_today?}`, all metric. 404 before the first fetch |
| `GET /api/v1/advisories` · `POST /api/v1/advisories/{id}/dismiss` | user, device | `AdvisoryView{id, text, severity, valid_from, valid_until, source}`. Dismiss publishes `advisory.updated` |
| `GET/POST /api/v1/weather-rules`, `PATCH/DELETE /api/v1/weather-rules/{id}` | adult | `WeatherRuleView{id, name, condition, action, severity, message, status, suggested_by, version}`. Invalid DSL → 422 with `{position, message}` |
| `POST /api/v1/weather-rules/validate` | adult | `{condition, message?}` → `{ok, error?{position, message}, preview?{matches, value, when}}` |
| `GET /api/v1/devices/{id}` · `PATCH /api/v1/devices/{id}` | adult | `DeviceView` + `settings: DashboardSettings` (Frontend.md §4.1, validated server-side: known orientation and theme, agenda_days 1..14, panels ≤ 12). Publishes `device.updated` |
| `GET /api/v1/dashboard?days=1..14` | device | `DashboardView{household, members[], events[], weather?, advisories[], settings}` |
| `GET /api/v1/status` | adult | `StatusView{sources[], weather{fetched_at?, ok}, backup, queue{ready, running, dead}}` |
| `GET /api/v1/stream` | user, device | M0 + the kinds in Feeds.md §6. Bridged from `fa_change` |

### Process config (T-08)
- `FA_GOOGLE_CLIENT_ID` and `FA_GOOGLE_CLIENT_SECRET` are optional; without them, Google is hidden in the UI.
- `FA_PUBLIC_URL` (needed for the OAuth redirect; e.g. `https://host.tailnet.ts.net`).
- `FA_OPEN_METEO_URL` (default `https://api.open-meteo.com`).
- `FA_ALLOW_HTTP_FEEDS` (default `false`).

### Jobs (kinds and default schedules)
| Kind | Owner crate | Default schedule |
|---|---|---|
| `calendar.sync_due` | fa-calendar | `* * * * *` |
| `calendar.sync{source}` | fa-calendar | enqueued |
| `calendar.prune` | fa-calendar | `30 3 * * *` |
| `weather.fetch` | fa-weather | `*/30 * * * *` (it enqueues `weather.evaluate`) |
| `weather.evaluate` | fa-weather | enqueued |

Each crate exposes `handlers() -> Vec<Arc<dyn JobHandler>>` and `default_schedules() -> Vec<(kind, cron)>`. `fa-server` registers them and ensures the schedules.

## Risks
| Risk | Mitigation |
|---|---|
| ICS and RRULE edge cases (floating times, TZID not in the IANA database, Outlook Windows tz names, COUNT combined with EXDATE) | T-05 builds a fixture corpus (the RFC 5545 examples, Google and Outlook exports, a fictional school feed). Unknown TZIDs map through a Windows→IANA table, and otherwise fall back to the household tz with a warning on the source |
| Google Testing-mode refresh tokens expire after 7 days | `needs_reauth` is surfaced on the status page and in the UI. ICS secret addresses are documented as the alternative (Feeds.md §3.1) |
| Separate api/worker processes hide SSE bugs that `serve all` would mask | The e2e stack runs `serve api` and `serve worker` as separate processes (T-12) |
| An Open-Meteo outage or rate limit | The last snapshot stays visible, `weather.ok=false` shows on the status page, and jobs back off |
| Contract drift between T-09 and T-10/T-11 | The types are generated from OpenAPI between the waves, and both briefs forbid hand-written API types |
| Disk space (12 GB free) | Check before each wave. Keep e2e images slim (Radicale is about 60 MB) |
