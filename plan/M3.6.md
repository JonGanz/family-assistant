# M3.6 Themes: Implementation Plan

## Why
The user wants an aesthetic colour system with depth: popular terminal palettes for the interface, and a named hue per member that each theme draws in its own shade (D-079, D-080). The theme is a per-device choice with no household setting, and the kiosk uses the same catalogue (D-081). The design is in `arch/Frontend.md` §3d.

## Done means
1. **Eight theme families ship** (Catppuccin, Nord, Dracula, Gruvbox, Solarized, Tokyo Night, Rosé Pine, Kanagawa) as data, each variant with the full token set, its source and licence recorded.
2. **A build-time test** checks every variant against the contrast rules of `arch/Frontend.md` §3d and fails the unit tests if one fails.
3. **Light/dark behaviour:** a family with one variant always uses it; with both, `auto` follows the device's `prefers-color-scheme` (kiosk: sunset and sunrise); a family with several variants in a mode lets the user pick one.
4. **App devices:** Settings → Personal → Appearance changes the theme live, saves it to `localStorage` (`fa.theme`), and survives a reload. Without a saved choice the shipped default (Catppuccin, `auto`) applies, and no flash of another palette appears at load.
5. **Kiosk:** the layout editor's theme control picks family, variant and mode and its live preview follows; the dashboard renders in that theme. Old saved layouts with `"theme": "auto"` still load.
6. **Members have a hue.** `Member.color` is one of the eight `Hue` names end to end (domain, store, API, TOML import and export, wizard, member picker, every chip and stripe). A new migration sets every existing member to `blue`. Calendar, task-list and category colours are unchanged.
7. Checklist of CLAUDE.md workflow 8: `scripts/ci-local.sh`, `scripts/e2e.sh` and `scripts/compose-smoke.sh` green; 0 dangling Docker volumes; README updated and its steps verified.

### Backend wire formats (T-02, used by T-03 and T-07)
- **`fa_domain::theme::Hue`**: `enum Hue { Red, Orange, Yellow, Green, Cyan, Blue, Purple, Pink }`, serde `rename_all = "lowercase"` (wire `"blue"`), `utoipa::ToSchema`, ts-rs exported, `Hue::ALL: [Hue; 8]`, `Hue::DEFAULT = Hue::Blue`, `Display` and `FromStr` for the lowercase name.
- **`Member.color`, `MemberDto.color`, `MemberPublicDto.color`, `NewMember`-style inputs, `NewSetupOwner.color`:** `Option<Hue>` (was `Option<String>`). Null means "unset"; the client draws unset as `blue`. Everything else called `color` (calendar, task list, category, mail category) stays `Option<String>`.
- **`fa_domain::theme::{ThemeChoice, ThemeMode}`**: `ThemeChoice { family: String, variant: Option<String> (omitted when none), mode: ThemeMode }`, `ThemeMode { Auto, Light, Dark }` (lowercase). `DashboardSettings.theme: ThemeChoice` replaces `DashboardTheme`.
  - Serialisation always writes the object form, e.g. `{"family":"catppuccin","mode":"auto"}`.
  - Deserialisation also accepts the legacy string `"auto" | "light" | "dark"`, mapped to `{family: DEFAULT_THEME_FAMILY, mode}`, so saved device layouts keep loading. Any other string still fails.
  - `pub const DEFAULT_THEME_FAMILY: &str = "catppuccin"`.
  - `validate()` also requires `family` and `variant` to match `^[a-z0-9][a-z0-9-]{0,31}$` (new `SettingsError::ThemeId`). The server does not know the catalogue: an unknown id is the client's fallback to its default.
- **Migration** `crates/fa-store/migrations/20261029000001_m36_member_hue.{up,down}.sql` (T-02 only): `UPDATE member SET color = 'blue' WHERE color IS NOT NULL`; then `ALTER TABLE member ADD CONSTRAINT member_color_hue CHECK (color IS NULL OR color IN ('red','orange','yellow','green','cyan','blue','purple','pink'))`. The down migration drops the constraint (the old colours are not restored).
- **API (T-03):** `CreateMemberReq.color: Option<Hue>`, `PatchMemberReq.color: Option<Option<Hue>>` (double option as today), the setup owner, and the dashboard member view all use `Hue`. A value that is not a hue name is `422`. OpenAPI registers `Hue`, `ThemeChoice` and `ThemeMode`.
- **TOML (T-03):** `MemberConfig.color: Option<Hue>`. Import also accepts a legacy `#rrggbb` string and maps it to `blue` (so old household files still import); export always writes the hue name. Calendar and category `color` in TOML stay hex.

### Web theme contract (T-04, used by T-05, T-06, T-07)
`apps/web/src/themes/types.ts`:
```ts
export const HUES = ['red','orange','yellow','green','cyan','blue','purple','pink'] as const
export type Hue = (typeof HUES)[number]
export type Mode = 'light' | 'dark'
export interface ThemeVariant {
  id: string            // slug, unique inside its family, e.g. 'mocha'
  label: string         // 'Mocha'
  mode: Mode
  neutrals: { bg: string; surface: string; surface2: string; border: string; muted: string; text: string; onAccent: string } // '#rrggbb'
  hues: Record<Hue, string>   // '#rrggbb'
}
export interface ThemeFamily {
  id: string            // slug, '^[a-z0-9][a-z0-9-]{0,31}$', e.g. 'catppuccin'
  label: string
  source: string        // URL of the published palette
  license: string       // SPDX id or name
  variants: ThemeVariant[]   // the first variant of each mode is that mode's default
}
export interface ThemeChoice { family: string; variant?: string; mode: 'auto' | 'light' | 'dark' }
```
`apps/web/src/themes/index.ts` exports: `FAMILIES` (from `./families`), `DEFAULT_CHOICE` (`{family: 'catppuccin', mode: 'auto'}`), `familyOf(id)`, `resolveVariant(choice, ctx: { prefersDark: boolean; night?: boolean }) → ThemeVariant` (unknown family falls back to the default family; a family with one variant ignores the mode; `auto` uses `night` when given, else `prefersDark`), `applyTheme(variant, el = document.documentElement)`, `loadDeviceChoice()`, `saveDeviceChoice(choice)`, and `useDeviceTheme()` (a composable holding the reactive choice, applying it, and reacting to `prefers-color-scheme` changes).
- **CSS custom properties** written by `applyTheme` (inline on `el`): `--color-bg`, `--color-surface`, `--color-surface-2`, `--color-border`, `--color-muted`, `--color-text`, `--color-on-accent`, `--hue-red` … `--hue-pink`, plus the aliases `--color-accent` (blue), `--color-focus` (blue), `--color-danger` (red), `--color-warning` (yellow), `--color-success` (green), and `data-theme-mode="light|dark"` on `el`. Existing token names in `styles/base.css` keep working.
- `themes/families/index.ts` exports `FAMILIES: ThemeFamily[]`. T-04 creates it with a **stub** (Catppuccin Latte and Mocha only); T-05 takes over `themes/families/**` and replaces the stub.
- `apps/web/src/dashboard/theme.ts` keeps `resolveTheme`, renamed `resolveMode`, and adds nothing else: `resolveMode(mode, now, sunrise, sunset, prefersDark) → 'light' | 'dark'` (the kiosk's night rule).
- **`localStorage` key** `fa.theme`: JSON of `ThemeChoice`; every read and write in try/catch.
- **Contrast rules** (tested in `themes/themes.test.ts`, T-04 writes the test, T-05 makes the data pass): `text` and `muted` on `bg`, `surface` and `surface2` at least 4.5:1; each hue on `bg` at least 3:1; `onAccent` on `hues.blue` at least 4.5:1. Reuse `lib/contrast.ts`.
