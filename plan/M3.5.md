# M3.5 Onboarding: Implementation Plan

## Why
D-065 (user instruction, 2026-10-26): installing takes Tailscale on the host, `tailscale serve`, a required HTTPS address, a hand-made master key and `.env`, a household TOML file, and `docker compose exec api fa-server ...` to import it and create logins. That is too much. M3.5 pauses feature work to fix it, before M4. It has three workstreams:

| | Workstream | In one line |
|---|---|---|
| **A** | Compose deployment, optional Tailscale sidecar | `docker compose up -d` with no required settings; `--profile tailscale` adds remote access |
| **B** | HTTPS optional | Plain HTTP on the home network works; HTTPS when Tailscale or a proxy provides it |
| **C** | First-run wizard | The first browser visit sets up the household, logins and access; no TOML, no CLI |

**This plan is written against the recommended option of each batch 18 question (Q-067 to Q-072) and Q-064 (batch 17).** When they are answered, run `process-answers`, re-derive Platform.md (T-01), then adjust the contracts below and write the task briefs. Any answer that differs from the recommendation is noted where it changes a contract.

## Done means
1. **Install in two commands.** On a machine with Docker: download `compose.yaml` (or clone), `docker compose up -d`. No `.env` edits, no key files, no build. Opening `http://<server>:8080` shows the wizard. Measured on the real server (H-13): under 15 minutes to a logged-in adult, excluding the image download.
2. **Tailscale is one profile.** `TS_AUTHKEY=... docker compose --profile tailscale up -d` puts the app on `https://<name>.<tailnet>.ts.net` with a real certificate, and ntfy on `:8443`. Without the profile, nothing Tailscale-related runs.
3. **HTTP and HTTPS both work.** Login, the dashboard, pairing, notifications and every e2e spec pass over plain HTTP from a LAN address, and over HTTPS behind a proxy. The session cookie is `Secure` exactly when the request arrived over HTTPS. Nothing refuses to start because of the scheme.
4. **The wizard replaces setup commands.** A fresh database shows `/setup`; finishing it leaves a household, its members, one adult login (plus optional others), PINs, the public address, notification settings and a confirmed master-key backup. `config import`, `user add` and `pin set` are no longer in the install guide (they remain for recovery and scripting).
5. **TOML stays optional.** Settings, System offers export (download) and import (upload with a dry-run preview), the same code paths as the CLI (D-018).
6. **Existing installs keep working.** Every current `FA_*` variable is still honoured and overrides the UI; an `api` + `worker` override file reproduces today's layout.
7. Checklist of CLAUDE.md workflow 8: `scripts/ci-local.sh`, `scripts/e2e.sh` (run by the main session) and `scripts/compose-smoke.sh` green; 0 dangling volumes; README and `deploy/README.md` verified by running them from an empty Docker host.

## Workstream A: compose deployment, optional Tailscale sidecar
**Target layout** (`deploy/compose.yaml`, replacing `compose.example.yaml`; `.env` becomes optional overrides only):

| Service | Profile | Image | Notes |
|---|---|---|---|
| `init` | default | `fa-server` | One-shot `fa-server init`: creates `master_key` and `db_password` in the `fa-secrets` volume if absent (Q-069). Exits 0. Others `depends_on: service_completed_successfully` |
| `postgres` | default | `pgvector/pgvector:pg16` | `POSTGRES_PASSWORD_FILE=/run/fa-secrets/db_password`. Not published |
| `app` | default | `ghcr.io/jonganz/fa-server:<tag>` | `serve all` (Q-071). Publishes `${FA_HTTP_PORT:-8080}` on `${FA_HTTP_HOST_IP:-0.0.0.0}` (Q-067). Reads the DB password from the secrets volume |
| `ntfy` | default | `binwiederhier/ntfy:v2.17.0` | Published on `${FA_NTFY_PORT:-8090}`; `NTFY_BASE_URL` set by the app's public address where possible, else the LAN address |
| `backup` | default | `prodrigestivill/postgres-backup-local:16` | Defaults to the named volume `fa-backups`; `BACKUP_DIR` overrides with a NAS path |
| `tailscale` | `tailscale` | `tailscale/tailscale:<pinned>` (name verified with `docker manifest inspect tailscale/tailscale:stable` on 2026-10-26; pin a version in T-04) | `TS_AUTHKEY`, `TS_HOSTNAME` (default `family`), `TS_STATE_DIR=/var/lib/tailscale` on volume `ts-state`, `TS_SERVE_CONFIG=/config/serve.json` (`deploy/tailscale/serve.json`: 443 → `http://app:8080`, 8443 → `http://ntfy:80`). Userspace networking, so no `NET_ADMIN` or `/dev/net/tun` |
| `ollama` etc. | `gpu`, `ai-cpu` | as today | unchanged |

- **Trusted proxy (Q-064):** the sidecar reaches `app` from its compose address. The compose network gets a fixed subnet and the sidecar a fixed IP; `FA_TRUSTED_PROXIES` defaults to loopback plus that IP, which also answers C-04 of the review.
- **`X-Forwarded-Proto`:** `tailscale serve` sets it; T-05 uses it (from trusted proxies only) for the cookie and for detecting the public address.
- **Image (Q-072):** `.github/workflows/release-image.yml` builds `linux/amd64,linux/arm64` with buildx on `v*` tags and pushes to GHCR. `build:` stays in a `compose.build.yaml` override for developers.
- **Host Tailscale** (today's way) stays in `deploy/README.md` as "Advanced: Tailscale on the host".
- **Override files:** `compose.split.yaml` (api + worker), `compose.build.yaml` (build locally), documented in `deploy/README.md`.

## Workstream B: HTTPS optional
- **`fa-config`:** drop the "https required unless localhost" startup error. `FA_COOKIE_SECURE` becomes `auto | true | false`, default `auto`. `FA_PUBLIC_BASE_URL` becomes optional (it overrides the stored setting).
- **Per-request scheme:** `auto` sets `Secure` when the request came over TLS, or from a trusted proxy with `X-Forwarded-Proto: https`. Never send HSTS.
- **Public address without config:** links that a request produces (pairing links, OAuth redirect) use the stored `public_base_url` setting, which the wizard fills from the browser's `location.origin` and Settings, System can change. Links produced without a request (notification click URLs in the worker) use the stored setting only. With the sidecar, both the LAN and tailnet addresses are stored, and pairing offers both (as D-064 does today).
- **LAN exposure (Q-067):** the full app on the LAN by default. A persistent "This connection is not encrypted" notice on the login page and in Settings when `!window.isSecureContext`. `lan_mode = full | dashboard_only | off` in Settings, System; `dashboard_only` reuses the D-064 guard on the main listener. PIN elevation over HTTP follows `lan_mode`; D-064's `FA_LAN_ALLOW_PIN` still applies to the separate listener.
- **Insecure-context audit of the web app (T-07):** no service worker registration when `!isSecureContext` (the app must load without it); replace `crypto.randomUUID`, `crypto.subtle` and `navigator.clipboard` uses with fallbacks; the PWA install hint hidden on HTTP.
- **Google sign-in** needs HTTPS (Google rejects `http://` redirect URIs except localhost). On HTTP, Settings shows Google as "needs HTTPS (turn on Tailscale)" instead of hiding it.
- **Child passwords (D-031):** the 4-character minimum stays, with a note on the not-encrypted notice; changing it would be a question.

## Workstream C: first-run wizard
**State:** setup is needed while no household exists. While needed, every `/api/v1/*` call except `/setup*`, `/healthz`, `/readyz` returns `409 {"error":"setup_required"}`, and the web router sends every route to `/setup`.

**Protection (Q-068):** the setup endpoints accept only clients whose peer address (or trusted-proxy client IP) is private, loopback or tailnet (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`), unless `FA_SETUP_REQUIRE_CODE=true` or `FA_SETUP_CODE` is set, in which case a code is also required. Once the first adult exists, `POST /setup` is gone for good (409).

**Steps** (each step saves; the wizard can be resumed, and back/next keeps values):
1. **Welcome.** Detected address, whether it's encrypted, whether the Tailscale sidecar is up.
2. **Household.** Name, time zone (browser default), location (city search through the Open-Meteo geocoding API, `geocoding-api.open-meteo.com/v1/search`, checked 2026-10-26; or lat/lon by hand), units, currency.
3. **You.** The first adult: display name, colour, username, password (12+), optional PIN. Creates the session; the rest of the wizard runs as that adult.
4. **Family.** Add adults and children (role, display name, colour, optional grade and aliases), each with an optional login and PIN. Reuses the Members page components.
5. **Access and notifications.** The public address(es), `lan_mode`, ntfy on or off with a "send a test" button (`notify test` today).
6. **Master key backup (Q-069).** Show the key as base64 with Copy and Download buttons; continuing requires ticking "I stored it somewhere safe". Settings, System warns until confirmed.
7. **Start.** Optional starter chores and routines (D-047), or "Import a household file" (TOML upload, dry-run preview first). Then links to Calendars, Mail, Devices (pair the wall screen).

**API contracts** (T-05; DTO wire formats fixed in the briefs):

| Method, path | Who | Does |
|---|---|---|
| `GET /api/v1/setup` | anyone allowed by the guard | `{needed, step, secure, detected_base_url, tailscale, code_required}` |
| `POST /api/v1/setup/household` | guard (+ code) | Creates the household (step 2). Only while no household exists |
| `POST /api/v1/setup/owner` | guard (+ code) | Creates the first adult member, account and session (step 3). Only while no adult account exists |
| `GET /api/v1/system/master-key` | adult, recently authenticated or elevated | The key as base64; audited |
| `POST /api/v1/system/master-key/confirm` | adult | Records the backup confirmation |
| `GET`, `PATCH /api/v1/system/settings` | adult | The runtime settings (Q-070), each with `{value, source: "db" \| "env"}`; env-set ones are read-only. Secrets are write-only |
| `POST /api/v1/config/import?dry_run=` | adult | TOML upload; the dry run returns what would change |
| `GET /api/v1/config/export` | adult | TOML download (no secrets, as today) |

Steps 4 to 7 use existing routes (`/members`, `/members/{id}/account`, `/members/{id}/pin`, `/household`, tasks templates) plus the settings route.

**Runtime settings (Q-070):** a new `instance_setting` table (system-scoped, not per household: `key text PK, value jsonb, secret_id NULL → secret, updated_at`). Keys: `public_base_url`, `tailnet_base_url`, `lan_mode`, `ntfy_url`, `ntfy_token` (secret), `google_client_id`, `google_client_secret` (secret), `allow_http_feeds`, `lan_dashboard` (D-064 fields), `trusted_proxies`, `key_backup_confirmed_at`. Resolution: env var > DB > default. Changes publish `pg_notify('fa_settings')`; the api and worker reload. The D-064 second listener and bind addresses need a restart, and the UI says so.

## Risks and open points
- **Plain HTTP is a real downgrade** for logins on a shared Wi-Fi. Q-067 makes it visible and configurable; the default follows the user's instruction.
- **Wizard hijack** on a LAN with untrusted devices: mitigated by Q-068 (address guard, optional code, one-shot).
- **Losing the secrets volume** loses the master key. The wizard step and the System warning (Q-069) exist for this; `restore.md` must cover it.
- **Q-061** (what comes next) proposed an M3.5 shakedown. This milestone takes the number; the shakedown becomes H-13/H-14 plus H-02 to H-11 on the new install.
- **Settings reload:** consumers that cache config at start (`AppState`, the worker's notify client) must read through the settings handle; T-01 lists each one.
