6. A weather rule with action `task` creates (or suggests) a task once per rule and day.
7. Notifications reach a **real ntfy container** in e2e: assigned, overdue, digest, quiet hours, batching, and children's copies. `notify test` works from the UI and the CLI.
8. The web app has Tasks, Routines, Settings → Tasks and Notifications, and calendar chips. The dashboard has the `now`, `member_tasks`, and `routine` panels, with completion through the member picker.
9. `config export` → `import` round-trips the new sections (topics excluded).

### Time semantics (fa-tasks; T-01's pure helpers implement them)
All dates are **local to the household time zone** (`household.tz`).
- **Due instant** of a due date `d`: `d` at `due_time`, or 23:59 when `due_time` is NULL. `visible_from` is local 00:00 of `d - lead_days`.
- **after_done:** the first due date is `start_date`. Completing or skipping at instant `t` sets `next_due_at` = due instant of `local_date(t) + interval_days`. Only completion sets `last_done_at`.
- **rrule:** instances are RRULE(`rrule`) with DTSTART `start_date` at `due_time` (00:00 when NULL), in the household tz. `next_due_at` is the next instance strictly after the occurrence just created (or consumed). Completion doesn't move it.
- **Season window:** a due date is in season when its MMDD lies in `[season_from, season_until]`, wrapping the year end when `from > until`. Outside it, `next_due_at` moves to the first in-season date (due instant), and for `rrule`, to the first in-season instance.
- **Condition:** `condition_ok = false` with `condition_checked_at` within 6 h defers creation (try again next minute). NULL or stale counts as true.

### Materialisation (fa-tasks, `tasks.materialize`, every minute, all households)
First, active definitions with `next_due_at IS NULL` (new from a config import, or after a schedule change) get it initialised as in the last paragraph. Then, for each active, unpaused definition with `now ≥ visible_from(next_due_at)`, in season, condition OK, inside a transaction that locks the definition row (`FOR UPDATE SKIP LOCKED`):
1. Find open or suggested occurrences of the definition.
   - `roll_over` with one open: create nothing. For `rrule`, advance `next_due_at` to the next instance (the instance is consumed). For `after_done`, leave it.
   - `auto_skip`: mark open ones `skipped` (`skipped_by` NULL = system), then create.
   - `pile_up`: create.
2. Create the task (`origin = system`, `due_at = next_due_at`, `visible_from`, steps from `steps_template`, `calendar_display` = the list's `calendar_default`, `priority_flag` from the definition). The `UNIQUE (definition_id, origin, due_at)` makes a repeat a no-op.
3. Assign (strategy below). Insert `assigned` outbox rows (§Notifications) for fixed and rotation assignees.
4. For `rrule`, advance `next_due_at`. For `after_done`, leave it (completion or skip moves it).
5. Publish `tasks.updated`.

New definitions get `next_due_at` = due instant of `start_date` (after_done) or the first instance ≥ now (rrule), moved into season.

### Strategies
| Strategy | Assign on create | On complete / skip |
|---|---|---|
| `fixed` | the one candidate, even if away (the API then marks the task `assignee_away: true`, so adults see it) | — |
| `rotation` | the first candidate at or after `rotation_cursor` (cyclic, by `ord`) who is not away on the due date. All away → the cursor candidate | advance: `rotation_cursor = (ord of the assignee + 1) % n` when (`any_completion`) or (`assignee_completion` and `completed_by` is the assignee). On skip only if `skip_advances` |
| `pool` | all candidates not away on the due date (all, if everyone is away) | — |

### Completion, skip, undo (fa-tasks)
- **Complete** (`member` = who did it): status `done`, `completed_at`, `completed_by`, `completed_via_device`; store `completion_undo`; stamp `last_done_at` and, for after_done, `next_due_at`; advance the rotation; clear the claim; publish.
- **Skip** (adults): status `skipped`, `skipped_by`; after_done → `next_due_at` from now; rotation per `skip_advances`.
- **Reopen**: within 10 minutes of `completed_at` it restores the definition from `completion_undo`, and deletes any occurrence of the same definition created after `completed_at` that is still open with no ticked steps. Later, it only reopens.
- **Claim** (pool members): `claimed_by`, `claimed_until` = now + `claim_ttl_minutes`, or local 23:59 today when NULL. **Release** clears it. `tasks.tick` clears expired claims.
- **Steps:** ticking every step does **not** auto-complete the task.

### Routines (fa-tasks)
- `routines.materialize` (every 15 minutes): for each routine and member, if today's local date qualifies (`fa_domain::routines::day_qualifies`), create today's run (idempotent by the unique key) with one `routine_run_step` per step. Open runs with `run_date` before today become `skipped`. Publish `routines.updated`.
- `school_days`: weekdays, minus days where `EventRepo::all_day_titles(school_calendar, date)` contains one of `no_school_match` (case-insensitive substring). No calendar → weekdays.
- Ticking the last step sets the run `done`. Unticking reopens it.

### Now score (fa-domain, pure)
`f(now)` = 0 before `visible_from`, rising linearly to 1 at `due_at`, then `1 + (now - due_at) / max(due_at - visible_from, 1 day)` capped at 2. No `due_at` → 0.3 (a constant for undated open tasks).
`score = w.due · f + w.flag · [high] + w.weather · [origin = weather]`. The Now list is the top `now_list_size` **open** tasks with `visible_from ≤ now` (or NULL), sorted by score descending, then `due_at`.

### Notifications
- **Producers (fa-tasks)** insert outbox rows with `INSERT … ON CONFLICT (household_id, dedupe_key) DO NOTHING`:
  | Trigger | When (job) | Recipient | dedupe_key | priority |
  |---|---|---|---|---|
  | `assigned` | occurrence created for fixed or rotation; a manual task created with assignees other than the creator | each assignee | `assigned:{task}:{member}` | 3 |
  | `overdue` | `tasks.tick`: open, `due_at < now` | each assignee | `overdue:{task}:{member}` | 4 |
  | `due_soon` | `tasks.tick`: open, `due_at - pref.due_soon_minutes ≤ now < due_at` | each assignee with the trigger on | `due_soon:{task}:{member}` | 3 |
  | `routine_nudge` | `tasks.tick`: open run with steps left, `done_by - pref.nudge_minutes ≤ now_local < done_by` | the run's member, trigger on | `nudge:{run}` | 4 |
  | `digest` | `tasks.digest` (every 15 min): local time ≥ the member's effective `quiet_until`, digest trigger on | the member | `digest:{member}:{local date}` | 2 |
- **fa-notify `notify.send`** (every minute): per pending row whose `not_before ≤ now`:
  1. no pref, or trigger disabled → `dropped`;
  2. in the member's effective quiet hours (pref override, else household) → leave pending, set `not_before` to the end of quiet hours;
  3. if `FA_NTFY_URL` is not configured → `dropped` with `last_error = 'not configured'`;
  4. batch each member's rows that are at least 60 s old into one message: one row → its title, body, priority, click; several → title `"{n} updates"`, body = the titles one per line, priority = the max, click `/tasks`;
  5. publish; success → `sent`; failure → attempts + 1, `not_before = now + 2^attempts min`, `failed` after 5 attempts;
  6. children with `copy_to_member_id`: insert a copy row for that adult (`dedupe_key = copy:{row id}`, title prefixed with the child's display name), which follows the adult's own rules.
- **`source_reauth`:** `notify.send` also inserts a row for every adult when a `calendar_source` has `state = needs_reauth` (`dedupe_key = reauth:{source}:{last_synced_at or 'never'}`).
- **ntfy publish** (verified against `binwiederhier/ntfy:v2.17.0` on 2026-10-25): `POST {FA_NTFY_URL}/{topic}` with body = message text and headers `Title`, `Priority` (1–5), `Tags`, `Click` (`FA_PUBLIC_BASE_URL` + `click_path`), plus `Authorization: Bearer {FA_NTFY_TOKEN}` when set. The response is JSON with an `id`. Read back with `GET /{topic}/json?poll=1&since=all` (one JSON object per line).
- **Topic:** 24 random characters `[a-z0-9]`, created by fa-notify when a member's prefs are first read or saved. The API shows it only to that member and to adults.

- **fa-notify `NotifyService`** (`new(store, NotifyConfig{ntfy_url: Option<String>, ntfy_token: Option<String>, public_base_url: String})`): `get_prefs(household, member) -> NotifyPrefView` (creates defaults and topic), `put_prefs`, `send_test(household, member) -> Result<(), NotifyError{NotConfigured, Publish(..)}>`, `handlers()`, `default_schedules()`.
- **fa-weather:** `validate_condition(&str) -> Result<(), ParseError>` (re-export of `parse`), plus the evaluate changes.

- Import is idempotent by name/title within a list, and `fa-server config import` validates RRULEs (through fa-tasks) and conditions (through fa-weather) before writing. **The example household stays without task data (D-047).**

## Risks
| Risk | Mitigation |
|---|---|
| Time-zone and DST errors in due instants and RRULE expansion | All date math in pure, unit-tested functions (T-01) with DST fixtures (Europe/London and America/New_York spring-forward days). RRULE expansion uses `rrule 0.14` with `Tz` |
| Minute-cadence jobs racing (materialize vs. complete) | Definition row lock (`FOR UPDATE SKIP LOCKED`), the `(definition_id, origin, due_at)` unique key, and idempotency keys |
| Notification floods (many tasks at once) | Outbox dedupe keys, 60 s batching per member, quiet hours |
| ntfy unreachable | Retries with backoff, `failed` after 5, visible in Settings → Status (queue counts) |
