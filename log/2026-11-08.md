## D-123: the UI picks up new versions after a deploy
The user reported that the UI often does not update after a deploy, worst on mobile and installed PWAs. Recorded as D-123 (from the instruction).

Causes:
- no Cache-Control on the static shell, so `index.html` was cached heuristically;
- the autoUpdate service worker never reloads an open page;
- the browser checks for a new service worker only on navigation.

Built:
- `fa-api` `shell_headers` middleware:
  - `no-cache` for `index.html`, `sw.js`, `registerSW.js`, the manifest and SPA routes;
  - `immutable` for `/assets/*`;
  - a 404 (no-store) for an `/assets/` miss instead of the SPA fallback;
  - `max-age=3600` otherwise;
  - `X-FA-Build` on every response.
- The stream sends `build {commit}` on connect.
- Web:
  - `lib/appUpdate.ts`: `sameBuild`, `noteServerBuild`, `applyUpdate` (SW update, then reload), `reloadApp`, `watchForUpdates` with a once-per-build loop guard;
  - `http.ts` and `kiosk/sse.ts` read the build;
  - `useFormDraft` keeps a global unsaved count (`hasUnsavedForms`);
  - `AppLayout` shows the notice when the snackbar is free, and reloads on foreground or navigation when safe;
  - the kiosk (`DashboardView`) reloads when idle (no dialog, not elevated);
  - Settings → About gets "Reload app".
- Arch: Frontend.md §1.0 and §5, Platform.md, the Frontend diagram.

Found on the way: the server's `build.rs` re-ran only when `.git/HEAD` changed, which a commit on the same branch never does. Local server builds therefore reported a stale commit; production Docker builds use the `GIT_COMMIT` arg and were unaffected. The new check saw the mismatch, and its snackbar hid the M2 e2e "done" toast. Fixed: `build.rs` watches the branch ref and packed-refs. The update notice now waits for a free snackbar.
